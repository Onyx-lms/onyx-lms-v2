## Executive summary

An institution was created from nothing and taken through a term's work by the four people who
would really do it. Every step is a real request against the live deployment, so every claim
below traces to something that happened rather than to an opinion.

**The authority model holds.** Ten attempts were made from the wrong side — a learner asking for
the roster, the fee ledger and the teaching allocations; a lecturer asking for the merchant
configuration; another institution's administrator asking for this one's course; an anonymous
caller asking for anything. All ten were refused with the right status. Four of those reads were
open a week ago, two of them returning an entire institution's data to any signed-in session.

**The money path holds.** A locked course refuses with `402` and opens the moment it is paid for.
Prices are typed in rupees and stored as integer minor units — ₹1,499 stores as `149900 INR`.

**The marking path holds.** A coding question authored against a Code Lab problem with a hidden
test case scored **10 out of 10 from the tests**, released immediately, with the candidate's own
submission readable afterwards.

One defect was found — a link to Fees still reachable by a learner from a second, hand-written
entrance — and was fixed and redeployed inside the pass.

## 2. The defect

<a id="d1"></a>
### D1 — Fees had a second entrance

**Severity:** Low · **Status:** fixed in `291ee82`, deployed and re-verified

Fees was removed from the learner's navigation on request. Driving the deployed site as a student
found the link still present in the dashboard's own **Quick links** list — written by hand in
`apps/web/src/app/onyx/dashboard/page.tsx`, independently of `apps/web/src/lib/onyx-nav.ts`, on
the first screen every learner sees.

```
FAIL  [6. the screens] a learner is not offered Fees in the navigation

  …<circle cx="16.5" cy="14.5" r="1.3"></circle></svg></span>Fees<span class="ml-auto…
```

The nav file was correct; a second list was not. The lesson is worth keeping:

> A navigation change is not finished until the hand-written link lists have been looked at too.

The rest of the product was swept for entrances of the same kind. There were none.

**Re-verified after deployment:** `ok [6. the screens] a learner is not offered Fees in the
navigation`.

## 3. What was attacked and held

### 3.1 Authority — 10 attempts, 10 refusals

| Attempt | As | Answer |
|---|---|---|
| Read the roster | Learner | `403` |
| Read teaching allocations | Learner | `403` |
| Read placement drives | Learner | `403` |
| Read fee structures | Learner | `403` |
| Create a course | Learner | `403` |
| Read fee structures | Lecturer | `403` |
| Read merchant configuration | Lecturer | `403` |
| Add a module to a course they do not teach | Lecturer | `403` |
| Read another institution's course | Administrator of a different institution | `404` |
| Read `/me`, `/members`, `/calendar` | Anonymous | `401` |

The lecturer refusals matter most: `fees.structures` and `fees.gateways` are declared with an
empty holders list, meaning no institution may ever delegate them below an administrator. Both
were readable by faculty and by the examinations office a week ago.

### 3.2 Permission for one person

The feature was exercised end to end rather than inspected:

1. `courses.create` was taken from `faculty` at the role level. Both lecturers were then refused
   — which is the problem the feature exists to solve, since the only lever was the role.
2. It was given back to **one named lecturer** through the screen.
3. The API then **accepted from her** exactly what it **still refused from her colleague**.

```
ok  one lecturer is given it back by name, and the other is not
ok  a grant is recorded against the person, not against the role
ok  a capability no role may ever hold is not offered for a person either
    → fees.structures: grantable=false
```

A grant is recorded on the membership, not on the tenant, so the same person can be faculty at
one institution and a student at another without carrying it across. A never-delegable capability
is not offered on the screen and is dropped by the API if requested directly.

### 3.3 Money

```
ok  creates a LOCKED course priced at ₹1,499        price_minor=149900
ok  cannot start a locked course without paying     402
ok  buys the locked course                          200
ok  the locked course opens after paying
```

Prices are typed in rupees with the currency symbol in the field, and converted on the way out.
The database still stores integer minor units, which is what keeps a ledger from drifting by a
paisa.

### 3.4 Marking, including code

Verified on a paper containing exactly one question — the code one — so the result is a fact
about marking rather than about which questions the paper happened to draw:

```
ok  Code Lab problem authored
ok  two test cases, one hidden
ok  problem published
ok  code question set
ok  the problem travels with the paper              problem=108
ok  handed in and marked by the tests               score=10/10
    review: response=present  awarded=10  released=true
```

**A note on the mixed paper.** The main run draws two questions from a four-question bank that
includes an essay, so roughly half of those runs produce `score=null` — the paper waits for a
marker. That is correct: instant release applies only where nothing needs a human. It is recorded
here because a single number from that run would misrepresent how the feature behaves.

### 3.5 Hardening

| Header | Value |
|---|---|
| `strict-transport-security` | `max-age=63072000; includeSubDomains; preload` |
| `x-content-type-options` | `nosniff` |
| `x-frame-options` | `SAMEORIGIN` |
| `content-security-policy` | `frame-ancestors 'self'` |
| `referrer-policy` | `strict-origin-when-cross-origin` |
| `permissions-policy` | `camera=(self), microphone=(), geolocation=(), payment=(self), interest-cohort=()` |

`camera=(self)` is deliberate and load-bearing. A copied-in policy of `camera=()` would switch off
live invigilation across the product, and the failure would present as a broken video connection
rather than as a header.

There is no full Content-Security-Policy, and that is a decision rather than an omission: App
Router hydration needs inline scripts, so a CSP without per-request nonces has to allow
`'unsafe-inline'` — a header that looks like protection and is not. `frame-ancestors` is the part
that is both meaningful and impossible to get subtly wrong. A real CSP needs nonce plumbing
through middleware and is outstanding work.

### 3.6 Experience

- **Zero** WCAG 2.1 AA violations across 20 screens in three roles.
- The first Tab on every role's landing screen reaches a skip link.
- No sideways scrolling at 390 px on the learner's four most-used screens.
- A wrong password shows an alert and does not move the page.
- Each role's landing screen leads with that role's own work.

## 4. Open items

None of these is broken code. Ranked by what they would cost.

<a id="o1"></a>
### O1 — The auth rate limit is too low to run an exam · HIGH

Signing in costs **two** calls to GoTrue: the password grant, and the refresh that scopes the
session to an institution. The project's current limit refuses at around the second round of five
people signing in together.

A hall of forty students starting an exam will hit it. They are now told to wait — the product
reports a rate limit as a rate limit rather than accusing them of a wrong password, which was
itself a defect fixed this week — but they still will not get in.

It is also why the automated browser suite cannot complete a single end-to-end run: it makes
several hundred sign-ins, and failures after that point are about the quota rather than the
product. Each area passes when run on its own.

**Fix:** raise **Authentication → Rate Limits → sign-ins** in Supabase. An institution behind one
NAT is one IP address.

<a id="o2"></a>
### O2 — The signup email may arrive with no code in it · HIGH

Custom SMTP is configured and a code is genuinely sent — verified against a live address. What
cannot be checked from here is the **body** of that mail: GoTrue includes the digits only if the
**Magic Link** template contains `{{ .Token }}`. A template carrying only the link delivers a
mail with nothing to type into the form.

**Fix:** add `{{ .Token }}` to the Magic Link template, register once, and read the mail.

<a id="o3"></a>
### O3 — Razorpay has never run against a real merchant account · MEDIUM

The gateway code is complete — order creation, HMAC signature verification, webhook parsing — and
no institution has credentials configured, so the real payment branch has only ever run against
the mock. Course purchase works today through that mock path, which is what §3.3 exercised.

**Fix:** test-mode keys in Settings → Payments; register the webhook at
`/api/onyx/payments/webhook/<tenantId>/razorpay` for `order.paid` and `payment.captured`; make one
test-mode purchase.

<a id="o4"></a>
### O4 — Two empty test institutions in production · LOW

`qa-cert-00701173` and `qa-cert-00810765`, both with **0 members**, left by an earlier
certification run.

Everything this pass created was removed, along with five leftover probe institutions from earlier
work this week. These two remain because deleting an institution is irreversible and the call
belongs to the owner.

**Fix:** confirm, and they go.

<a id="o5"></a>
### O5 — Marker comments are written and never shown · LOW

The staff marking form writes `marker_comment` per question. No learner-facing route serves it, so
a marker's feedback reaches nobody. The paper page no longer promises it — the copy was corrected
— but delivering it is outstanding work rather than a decision.

## 5. Where the product could be better

Ranked by how much they would change somebody's day, not by effort.

### A whole-hall invigilation view

Live camera invigilation works and is **one candidate at a time**, because the media is
peer-to-peer and a browser will not hold forty inbound streams. The limit is real, and the
interface reports it honestly — but it is not what an invigilator wants during an examination. A
wall of forty needs an SFU, which this deployment does not have. Worth costing before the next
exam season rather than during it.

### A TURN relay

Without one, a candidate behind a symmetric NAT or a strict corporate firewall cannot be reached
at all. The viewer says so rather than showing a black rectangle, but "some candidates cannot be
watched" is a poor answer on exam day. TURN is bandwidth somebody pays for, and a small monthly
cost against the alternative.

### Question-level feedback for learners

The data exists — `auto_points`, `manual_points` and `marker_comment` per answer — and two thirds
of it now reaches the candidate. The comment is the part that would actually teach somebody
something, and it is the part still missing. See [O5](#o5).

### Papers with no closing date never appear on the timetable

An always-open practice paper has no day it belongs to, so the week cannot place it. That is
correct for a calendar and leaves those papers with no presence on the one screen a learner checks
for what is due. A "no fixed date" list beside the grid would close it.

### The rate limit should be visible before it bites

The product now says "too many people are signing in at once" instead of accusing somebody of a
wrong password. An administrator still has no way to see how close their institution is to the
ceiling until it is reached. See [O1](#o1).

### An API asymmetry worth tidying

`/api/onyx/platform/tenants/:id/courses` accepts `POST`, `PATCH` and `DELETE` and has no `GET`
beside them; the platform console reads `/academics` instead. No screen needs the missing route
and nothing is broken — but the next person to reach for it will assume it exists, as this pass
did.

## 6. Method and reproduction

Two scripts and one browser spec, all run against the deployed site:

| File | What it does |
|---|---|
| `qa-live/flows.mjs` | The 97 flow checks. Creates one institution, drives four roles through it, attacks it from the wrong side, and removes nothing — cleanup is deliberate and separate. |
| `qa-live/coding.mjs` | The coding path on a single-question paper, so the marking result cannot depend on the draw. |
| `tests/browser/zz-qa-ux.spec.ts` | Accessibility, keyboard, mobile overflow, error handling and landing screens, in real Chromium. |

All three take `QA_BASE` and default to the production URL:

```
QA_BASE=https://onyx-lms-v2.vercel.app node qa-live/flows.mjs
QA_BASE=https://onyx-lms-v2.vercel.app node qa-live/coding.mjs
QA_BASE=https://onyx-lms-v2.vercel.app npx playwright test tests/browser/zz-qa-ux.spec.ts
```

Results are written to `qa-live/results.json` and `qa-live/ux.json`.

**Tokens are minted once per person and reused.** Signing in costs two calls to GoTrue, and a run
that trips the rate limit reports failures about the quota rather than about the product — see
[O1](#o1).

**Test data.** Everything created by this pass was deleted afterwards: three QA institutions and
their 24 accounts, plus five leftover probe institutions from earlier work. The demo institutions
were read but never written to. What remains is listed in [O4](#o4).
