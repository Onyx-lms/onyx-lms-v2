## Executive summary

An institution was created from nothing and taken through a term's work by the four people who
would really do it. Every step is a real request against the live deployment, so every claim
below traces to something that happened rather than to an opinion.

**The authority model holds.** Ten attempts were made from the wrong side — a learner asking for
the roster, the fee ledger and the teaching allocations; a lecturer asking for the merchant
configuration; another institution's administrator asking for this one's course; an anonymous
caller asking for anything. All ten were refused with the right status.

**The money path holds.** A locked course refuses with `402` and opens the moment it is paid for.
Prices are typed in rupees and stored as integer minor units — ₹1,499 stores as `149900 INR`.

**The examination path was driven on its own, and now holds end to end.** A bank of all six
question types, a paper drawn from the whole of it, a sitting scheduled against that paper, the
window the two share, the slot the sitting owns on the timetable, a candidate sitting it, the
machine's marking at hand-in, a marker's correction afterwards, and the office's mark sheet:
**87 checks, 87 pass**. Two of this pass's three defects were found down that path.

Three defects were found in total, all fixed and redeployed inside the pass — and one of them was
a candidate losing the marks for a coding question they had answered correctly.

## 2. Defects found and fixed

<a id="d1"></a>
### D1 — Fees had a second entrance

**Severity:** Low · **Status:** fixed in `291ee82`, deployed and re-verified

Fees was removed from the learner's navigation on request. Driving the deployed site as a student
found the link still present in the dashboard's own **Quick links** list — written by hand in
`apps/web/src/app/onyx/dashboard/page.tsx`, independently of `apps/web/src/lib/onyx-nav.ts`, on
the first screen every learner sees.

```
FAIL  [6. the screens] a learner is not offered Fees in the navigation
  …<circle cx="16.5" cy="14.5" r="1.3"></circle></svg></span>Fees<span class="ml-auto…
```

The nav file was correct; a second list was not.

> A navigation change is not finished until the hand-written link lists have been read too.

**Re-verified:** `ok [6. the screens] a learner is not offered Fees in the navigation`.

<a id="d2"></a>
### D2 — A code answer the sandbox could not run was silently marked zero

**Severity:** High · **Status:** fixed in `04da989`, deployed and re-verified

The most serious thing found this pass, and it was found by driving the deployed site rather than
by reading code.

`AssessService.saveAnswer` tested `response.source` and fell through when there was none. So a
client that sent the candidate's program as a **bare string** — which is what every other question
type takes — had it written to the answer row with no Code Lab submission behind it, and was told
the answer was saved. It was: as a blob nothing could run.

`#finalise` then did the right thing with the wrong input. It saw a code answer with no
submission, sent the attempt to a marker, and left that question at zero. Nothing anywhere said
why. On a mixed paper the candidate simply lost ten marks:

```
essay      auto=null  manual=18   points=20
multiple   auto=5                 points=5
truefalse  auto=5                 points=5
single     auto=5                 points=5
short      auto=5                 points=5
code       auto=null  manual=null points=10   ← answered correctly, never run
```

**The fix.** A code answer that cannot be graded is now refused with `422` and a message naming
the shape, rather than stored. Refusing costs the candidate nothing — the attempt is not spent and
the clock is untouched — where the old behaviour cost them the marks.

`normaliseCodeAnswer` is generous before it is strict: a bare string is taken whole where the
problem allows exactly **one** language, because there is nothing to guess at then. Where a
problem accepts several, guessing would compile Python as C++ and score the same honest zero, so
it says what is missing instead.

**Re-verified live, on a mixed six-question paper:**

```
ok  a code answer the sandbox cannot run is refused rather than stored
    422 That is not a code submission. Send the language you are writing in and
        your program, and it will be run against the tests.
ok  the coding answer was marked by its tests, hidden case included    awarded=10/10
ok  the total now includes the essay                                   score=46/50
```

<a id="d3"></a>
### D3 — The marker's comment was written to nobody

**Severity:** Low · **Status:** fixed in `b17a9fe`, deployed and re-verified

`marker_comment` has been written per question by the staff marking form for as long as marking
has existed, and served by nothing. A marker explaining why an essay lost four marks was writing
into the void. It was carried in the previous report as an open item filed as a gap rather than a
decision; it is now closed.

`attemptForCandidate` returns it and the review screen renders it, labelled as a person's words
rather than dropped in as more grey prose — distinct from the question's own explanation, which
reads the same for everybody who sat the paper.

Released on **exactly** the condition the score is released on, and there is a test for that half
too: a comment is a mark in prose, and *"you have misread the question"* before the paper is out
tells a candidate their result early, in a form no moderation pass can quietly revise first.

```
ok  and the marker's comment reaches them
    comment="The tilt is right; say more about why the angle matters."
```

## 3. The examination path, on its own

The sweep touches examinations in passing and draws two questions from a four-question bank — so
which questions a candidate meets, and therefore whether the result is instant or waiting on a
marker, **differs between runs**. A single number from that harness would misrepresent how the
feature behaves.

`qa-live/exams.mjs` goes down the examination path and nothing else, and every paper in it takes
its whole bank. A failure there means something changed, not that the dice fell differently.

### What that proves, in the harness's own words

```
ok  the coding question kept its problem                      problem_id=110
ok  a coding question with no problem is refused              expected 422, got 422
ok  the paper took the sitting's window                       opens=… closes=…
ok  and the window is the sitting's length, not the paper's   90 minutes
ok  an examination cannot borrow another course's paper       expected 422, got 422
ok  an examination on it is scheduled, with no term named     200 semester_id=null
ok  the examination is on it                                  Finals sitting mt6o88e3
ok  and the ninety minutes it occupies, so it owns a slot     duration=90
ok  the candidate sees the sitting on their own week          1 sittings
ok  the coding question arrives with its problem, and no tests
ok  the objective questions were marked by machine at hand-in single=5 multiple=5 truefalse=5 short=5
ok  the coding answer was marked by its tests, hidden case included   awarded=10/10
ok  a paper with an essay on it is held for the marker        status=submitted score=null
ok  marking alone does not release it                         score=null
ok  the candidate sees the mark once it is out                score=46
ok  and the marker's comment reaches them
ok  the answer key appears now there is no resit left         expected="a"
ok  and the result does not vanish while it is improved       score=48
```

Four rules worth naming, because each is a thing that could plausibly have been built the wrong
way and was not:

- **An examination owns a slot, not a day.** The sitting carries its own start and its own ninety
  minutes onto the calendar, and the paper's window is pulled to match it — including when the
  sitting is brought forward afterwards.
- **Instant release stops where a person is needed.** A paper with an essay on it is held, whatever
  the switch says. Marking it does not release it either; a person releases it.
- **A released result does not vanish when it is improved.** A marker correcting a released mark
  changes the number and leaves it out.
- **The key waits for the last sitting.** With one attempt allowed and one taken, the correct
  answers appear; with a resit still to come they would not.

### 4.4 Hardening

| Header | Value |
|---|---|
| `strict-transport-security` | `max-age=63072000; includeSubDomains; preload` |
| `x-content-type-options` | `nosniff` |
| `x-frame-options` | `SAMEORIGIN` |
| `content-security-policy` | `frame-ancestors 'self'` |
| `referrer-policy` | `strict-origin-when-cross-origin` |
| `permissions-policy` | `camera=(self), microphone=(), geolocation=(), payment=(self), interest-cohort=()` |

`camera=(self)` is deliberate and load-bearing. A copied-in policy of `camera=()` would switch off
live invigilation across the product, and the failure would present as a broken video connection
rather than as a header.

There is no full Content-Security-Policy, and that is a decision rather than an omission: App
Router hydration needs inline scripts, so a CSP without per-request nonces has to allow
`'unsafe-inline'` — a header that looks like protection and is not. A real CSP needs nonce plumbing
through middleware and is outstanding work.

## 5. Open items

None of these is broken code. Ranked by what they would cost.

<a id="o1"></a>
### O1 — The auth rate limit is too low to run an exam · HIGH

Signing in costs **two** calls to GoTrue: the password grant, and the refresh that scopes the
session to an institution. The project's current limit refuses at around the second round of five
people signing in together.

A hall of forty students starting an exam will hit it. They are told to wait — the product reports
a rate limit as a rate limit rather than accusing them of a wrong password, which was itself a
defect fixed this week — but they still will not get in.

It is also why the automated browser suite cannot complete a single end-to-end run: it makes
several hundred sign-ins, and failures after that point are about the quota rather than the
product. Each area passes when run on its own.

**Fix:** raise **Authentication → Rate Limits → sign-ins** in Supabase. An institution behind one
NAT is one IP address.

<a id="o2"></a>
### O2 — The signup email may arrive with no code in it · HIGH

Custom SMTP is configured and a code is genuinely sent — verified against a live address. What
cannot be checked from here is the **body** of that mail: GoTrue includes the digits only if the
**Magic Link** template contains `{{ .Token }}`. A template carrying only the link delivers a mail
with nothing to type into the form.

**Fix:** add `{{ .Token }}` to the Magic Link template, register once, and read the mail.

<a id="o3"></a>
### O3 — Razorpay has never run against a real merchant account · MEDIUM

The gateway code is complete — order creation, HMAC signature verification, webhook parsing — and
no institution has credentials configured, so the real payment branch has only ever run against
the mock. Course purchase works today through that mock path, which is what §4.3 exercised.

**Fix:** test-mode keys in Settings → Payments; register the webhook at
`/api/onyx/payments/webhook/<tenantId>/razorpay` for `order.paid` and `payment.captured`; make one
test-mode purchase.

<a id="o4"></a>
### O4 — Two empty test institutions in production · LOW

`qa-cert-00701173` and `qa-cert-00810765`, both with **0 members**, left by an earlier certification
run.

Everything this pass created was removed. These two remain because deleting an institution is
irreversible and the call belongs to the owner.

**Fix:** confirm, and they go.

## 6. Where the product could be better

Ranked by how much they would change somebody's day, not by effort.

### A whole-hall invigilation view

Live camera invigilation works and is **one candidate at a time**, because the media is
peer-to-peer and a browser will not hold forty inbound streams. The limit is real, and the
interface reports it honestly — but it is not what an invigilator wants during an examination. A
wall of forty needs an SFU, which this deployment does not have. Worth costing before the next exam
season rather than during it.

### A TURN relay

Without one, a candidate behind a symmetric NAT or a strict corporate firewall cannot be reached at
all. The viewer says so rather than showing a black rectangle, but "some candidates cannot be
watched" is a poor answer on exam day. TURN is bandwidth somebody pays for, and a small monthly
cost against the alternative.

### Papers with no closing date never appear on the timetable

An always-open practice paper has no day it belongs to, so the week cannot place it. That is
correct for a calendar and leaves those papers with no presence on the one screen a learner checks
for what is due. A "no fixed date" list beside the grid would close it.

### The rate limit should be visible before it bites

The product now says "too many people are signing in at once" instead of accusing somebody of a
wrong password. An administrator still has no way to see how close their institution is to the
ceiling until it is reached. See [O1](#o1).

### An API asymmetry worth tidying

`/api/onyx/platform/tenants/:id/courses` accepts `POST`, `PATCH` and `DELETE` and has no `GET`
beside them; the platform console reads `/academics` instead. No screen needs the missing route and
nothing is broken — but the next person to reach for it will assume it exists, as this pass did.

## 7. Method and reproduction

Three harnesses and one generator, all run against the deployed site:

| File | What it does |
|---|---|
| `qa-live/flows.mjs` | The 97-check sweep. Creates one institution, drives four roles through it, and attacks it from the wrong side. |
| `qa-live/exams.mjs` | The 87-check examination path, with nothing drawn at random — see §3. |
| `tests/browser/zz-qa-ux.spec.ts` | Accessibility, keyboard, mobile overflow, error handling and landing screens, in real Chromium. |
| `qa-live/report-pdf.mjs` | The printable report. Every figure is read out of the evidence files, so the document cannot drift from the run that produced it. |

```
QA_BASE=https://onyx-lms-v2.vercel.app node qa-live/flows.mjs
QA_BASE=https://onyx-lms-v2.vercel.app node qa-live/exams.mjs
QA_BASE=https://onyx-lms-v2.vercel.app npx playwright test tests/browser/zz-qa-ux.spec.ts
node qa-live/report-pdf.mjs
```

Evidence lands in `qa-live/results.json`, `qa-live/exams.json` and `qa-live/ux.json`.

**Tokens are minted once per person and reused.** Signing in costs two calls to GoTrue, and a run
that trips the rate limit reports failures about the quota rather than about the product — see
[O1](#o1).

### What this does not cover

- **Payments were exercised through the mock, not a merchant account** — see [O3](#o3).
- **Invigilation was driven as far as its queue.** No camera or screen-share session was carried
  end to end.
- **Accessibility was automated.** axe on 20 screens plus keyboard and mobile checks; no
  screen-reader walkthrough, and axe catches a minority of real barriers.
- **Load and concurrency were not tested.** Timings are single-user navigations.

**Test data.** Everything created by this pass was deleted afterwards. What remains is listed in
[O4](#o4).
